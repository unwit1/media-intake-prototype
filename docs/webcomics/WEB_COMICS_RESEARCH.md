# Webcomics ecosystem research

Investigated 2026-09-29. This is a dated assessment, not a promise that every upstream extractor still works. See [provider coverage](WEB_COMICS_PROVIDER_MATRIX.md), [architecture](WEB_COMICS_ARCHITECTURE.md), [metadata](WEB_COMICS_METADATA_SOURCES.md), [backlog](WEB_COMICS_ROADMAP.md) and [adapter authoring](WEB_COMICS_ADAPTER_GUIDE.md).

## Method and repository findings

Searched GitHub broadly for webcomic, ComicFury, WEBTOON, Tapas, archive, Smack Jeeves, comic metadata and reader extensions; inspected project READMEs, licenses, public source files, official API documentation and activity through the GitHub repository API. `research/upstream-snapshot.json` records exact upstream `pushed_at`, archived flag, license detection, language and references. Refresh facts with `python tools/research_webcomics.py`. A pushed date is an activity signal, not proof of maintenance quality. Unknown licenses and failed lookups remain explicit.

The app is Python/Tkinter, with standard-library HTTP/XML/HTML, SQLite `items` and `watched_items`, a media relationship graph, optional dependencies and an existing four-worker book pool. Comic feeds, MangaDex, Taddy/3S and Comic Vine were already implemented. `serial.py` already parses RSS/Atom/JSON Feed, discovers feeds, validates image signatures and creates CBZ/ComicInfo. Existing user edits were present at inspection. Integration must preserve them, preserve legacy watches, and avoid a second scheduler.

## Architecture evidence and decisions

Reviewed [Dosage scraper boundaries](https://github.com/webcomics/dosage/blob/main/dosagelib/scraper.py), [gallery-dl WEBTOON](https://github.com/mikf/gallery-dl/blob/master/gallery_dl/extractor/webtoons.py), [Tapas](https://github.com/mikf/gallery-dl/blob/master/gallery_dl/extractor/tapas.py), [yt-dlp common extractor](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/common.py), source registries and project docs above. Borrow the separation of discovery, entry metadata, asset resolution, download state and extension dispatch. Keep our normalized records independent of downloader-specific naming conventions.

The first implementation is dependency-free and reuses the app's feed parser and queue. Explicit adapters plus validated JSON recipes are a better immediate fit than embedding a large downloader, a browser runtime, or arbitrary executable extensions. No `SUBSUME` decision was justified: upstream support breadth does not provide durable watching, field provenance or this app's migrations automatically.

The desired resolver order remains public API → structured metadata → feed → sitemap → platform → archive HTML → recipe → DOM candidate → bounded browser → manual map. Implemented now: xkcd public API, structured metadata enrichment, feed autodiscovery, platform/static/recipe extraction. Sitemap, generic layout inference and browser rendering are explicit backlog items. Structured covers are never silently imported as comic pages.

## Reuse and attribution ledger

No third-party runtime code copied or vendored. All new subsystem code is independently implemented; existing repository `serial`, `core`, `watched` and rights/graph abstractions are reused. No new dependency was installed. No GPL/AGPL source incorporated. The repository did not expose a root license during inspection, so do not assume license compatibility for future copying. A future borrowed component must record repository, immutable commit/version, exact files, license text, modifications and required notices in `licenses/` and here.

No publicly accessible page implies public-domain rights. The app's existing source/per-work configuration applies to archive jobs. Protected connectors belong behind legitimate user sessions and credentials; this subsystem implements no access-control bypass.
